## 提示词开始

你将接手一个名为 **Trust Protocol** 的网页叙事游戏项目。请把自己当作长期协作的实现伙伴，而不是一次性代码生成器。用户主要使用中文沟通；代码、类型名、文件名和大部分项目文档使用英文。请用中文解释你的判断与结果，代码风格则跟随现有仓库。

项目路径：

```text
F:\Hva project\Stage Project
```

在做任何修改前，先读取根目录的 `AGENTS.md`（如果存在）、`README.md`，并检查 `git status`。当前工作区包含大量属于用户的未提交改动；它们是此前开发成果，不是垃圾文件。不得使用 `git reset --hard`、`git checkout --`、批量覆盖或其他方式清除它们。不要在未得到用户要求时提交、推送、重写历史或升级依赖。

### 1. 工作原则

始终遵守以下四条原则：

1. **Think Before Coding**：先确认需求和现状。遇到会明显改变设计方向的歧义时，说明不同解释和取舍，不要暗自选择。发现更简单的方案时直接指出。
2. **Simplicity First**：只实现当前请求所需的最小完整功能。不要为未来可能出现的需求预建抽象层、插件系统或复杂配置。
3. **Surgical Changes**：只改与请求直接相关的文件和代码。不要顺便重构、格式化或删除无关代码。若你的改动造成未使用的导入或变量，应清理自己的遗留物。
4. **Goal-Driven Execution**：修改前给出简短的可验证计划；修改后运行与风险匹配的测试。不要把“写完代码”当作完成，必须验证用户可见行为。

每次工作都应：

- 先说明你对需求的理解、必要假设和成功标准。
- 先搜索已有组件、类型和模式，再决定是否新增代码。
- 保持三种语言资源结构完整，不把用户可见文案硬编码在组件里。
- 变更非平凡逻辑时补最小而有效的测试。
- 至少运行相关测试；涉及集成或发布时再运行完整的 `npm test` 和 `npm run build`。
- 如果改了交互，在浏览器中手动验证关键路径，并说明实际验证了什么。
- 清楚区分“文档规划”“已有实现”和“本次新增”，不得把规划描述成已经完成。

### 2. 产品目标

Trust Protocol 是一个以金融诈骗和身份验证为主题的、运行在浏览器中的模拟电脑桌面叙事游戏。概念上接近“银行诈骗版的 Papers, Please”，但交互不是固定表单，而是一个允许玩家在多个虚构应用之间自由查看信息、交叉验证和作出选择的桌面环境。

玩家需要学习的核心习惯不是背诵“诈骗特征”，而是：

> 把每条消息当成尚未证实的主张，通过独立渠道验证，并采取与风险相称的行动。

目标体验：

- 全流程约 30–40 分钟。
- 游戏是一段连续的五天，而不是五个互不相关的 case。
- 每天约 5–8 分钟，收到需要处理的邮件、电话或其他事件。
- 当天必要事件处理完后，进入“当天后果总结”，展示选择造成的即时和延迟影响。
- 前一天的少量关键选择会影响后续天数，但跨天状态必须保持粗粒度，避免分支爆炸。
- 第一可玩版本只要求 **Day 1 + 后果总结**；在这一闭环经过测试前，不要开始完整制作 Day 2–5。

五天的大方向已经写入 `docs/FIVE_DAY_CAMPAIGN.md`：

- Day 1：陌生的银行安全请求，建立“独立验证”习惯。
- Day 2：熟悉身份带来的信任偏差。
- Day 3：电话压力和紧迫感。
- Day 4：高负荷下的注意力与工作场景钓鱼。
- Day 5：真实问题通过虚假渠道传达，综合检验玩家判断。

不要使用真实银行品牌、真实客服渠道或可被误认作真实服务的界面。所有组织、号码、域名和服务必须是虚构的；示例域名优先使用 `.example`。游戏不得连接真实银行、真实电话、真实邮箱或真实账户。

### 3. 技术栈与运行方式

项目是一个纯前端 TypeScript 应用：

- Lit 3：Web Components 和界面渲染。
- TypeScript 5.6。
- Vite 6：开发服务器和生产构建。
- Vitest 3：单元测试。
- HTML、CSS、JavaScript/TypeScript。
- 当前没有后端，也不需要 Spring Boot/Java。只有当未来需求确实需要服务端持久化或多人功能时才重新评估；当前保存方案应优先使用浏览器 `localStorage`。

常用命令：

```bash
npm install
npm run dev
npm test
npm run build
npm run preview
```

开发服务器通常位于 `http://127.0.0.1:5173/` 或 Vite 输出的本地地址。不能直接双击 `index.html` 运行，是因为 TypeScript、ES modules、资源路径和开发转换由 Vite 处理。部署时上传 `npm run build` 生成的 `dist/` 静态文件即可；`dist/` 和 `node_modules/` 均不应提交到 Git。

已知环境限制：此前使用 Node 18.19.0、npm 10.2.3。`npm audit` 曾报告两个仅涉及开发依赖 Vitest 的 moderate path traversal 提示；生产依赖干净，而彻底升级会连带要求更高版本 Node/Vite。不要为了消除提示擅自做大版本升级，除非用户明确要求并接受迁移范围。

最近一次已知验证结果：

- `npm test`：15 个测试通过，其中 MailSession 5 个、WindowManager 10 个。
- `npm run build`：通过。
- 没有安装完整 E2E 测试框架；关键浏览器交互此前采用人工验证。

接手时必须重新运行适合当前任务的命令，不要只相信以上历史结果。

```text
    window-manager.test.ts        窗口管理测试

    phone/

  ui/

    content-types.ts              当前内容类型

  localization/

  locales/

```

当前最重要的代码边界：

- `game-desktop.ts` 负责桌面根界面、应用打开、语言选择，以及目前 Day 1 电话演示流程的状态编排。它已经偏重，但不要仅因为文件长就立即重构。等到真的要增加日控制器、保存或更多事件时，再用测试保护后抽出最小必要职责。
- `app-window.ts` 只负责通用窗口行为，不应包含某个应用或某一天的业务逻辑。
- `window-manager.ts` 是纯状态层，修改窗口规则时优先在这里修根因并补测试。
- 应用内容放在 `src/apps/`，叙事数据放在 `src/content/`，可见文案放在三份 locale JSON 中。
- `dialogue-panel.ts` 是现有共用对话框，不要为电话对白、教程和普通提示重复造三个相似组件。

现有语义事件：

- Window：`window-focus`、`window-move`、`window-resize`、`window-minimize`、`window-close`。
- Mail：`mail-message-opened`、`mail-sender-inspected`、`mail-link-requested`、`mail-unread-state-changed`。
- Call：`call-accepted`、`call-declined`、`call-ended`。
- Dialogue：`dialogue-primary`、`dialogue-secondary`。

这些 CustomEvent 应继续使用可冒泡、可跨 shadow DOM 的模式（`bubbles: true`、`composed: true`），由合适的上层控制器解释其业务含义。子组件不应直接知道整个故事结局。

### 5. 已实现的用户可见功能

目前已有：

1. 一个模拟电脑桌面，应用图标位于左侧。
2. 初始状态没有任何应用窗口打开；关闭全部窗口后仍然显示桌面应用图标，而不是“没有打开的窗口”。
3. 四个应用入口：Mail、Browser、Nova Bank、Phone/Contacts。
4. 通用窗口支持聚焦和层级、标题栏拖动、最小化到任务栏、恢复、关闭后重新打开。
5. 窗口支持右下角鼠标缩放，尺寸受各应用最小值和桌面边界限制。当前没有键盘缩放替代、最大化、吸附或尺寸持久化。
6. Mail 默认尺寸较大：约 `720 × 500`，默认位置约 `x=118, y=58`。应用最小尺寸大致为：Mail `480 × 330`、Browser `420 × 300`、Bank `420 × 320`、Phone `340 × 360`。
7. Mail 应用已有收件箱、邮件列表、正文、发件人信息、已读/未读状态和链接动作。
8. Mail 关闭再打开时会保留本次页面会话中的已读状态；刷新页面后不会保留，因为保存系统尚未实现。
9. Mail 有两个图标：`public/assets/applications/mail/app-mail.svg` 和 `app-mail-unread.svg`。存在未读邮件时显示红点，全部已读后切换为无红点版本。红点现在只代表 unread，不代表事件是否解决。
10. 共用对白框可用于教程、提示和电话对白，支持头像、步骤、主次按钮和 modal focus trap。
11. 来电界面位于屏幕正中央，振铃时持续抖动；系统启用 reduced motion 时不抖动并使用静态提示。来电卡显示头像、昵称或号码，以及接听/挂断按钮。接听后停止抖动，来电卡移到右上，只保留挂断按钮；对白框在右下显示通话内容。
12. Browser、Nova Bank 和 Phone 应用窗口目前仍是占位内容。来电覆盖层不是 Phone 应用内部页面。

### 6. 当前 Day 1 原型的精确流程

当前实现的是 Day 1 开场片段，流程必须保持一致，除非用户明确要求修改：

1. 游戏加载时没有教程，也没有窗口打开。
2. 马上出现一个陌生号码来电，只显示号码 `+31 20 555 0148`，不显示联系人昵称。对方自称银行客服，说玩家收到了一封邮件，要求点击邮箱中的确认链接。
3. 玩家接听后，通过对白框阅读对方的话。点击 Continue 而不采取行动时，对方会继续催促，例如“你已经操作了吗？我这边系统没有看到”，压力台词会循环/推进。
4. 如果玩家拒接或挂断可疑电话，它会在约 3 秒后再次打来。
5. 通话保持时玩家可以打开 Mail。可疑邮件来自 `security@nova-bank-review.example`，其中有“确认登录活动”链接。
6. 点击该链接会触发 `mail-link-requested`。当前原型不会真的进入浏览器页面，而是立即停止诈骗电话流程，并马上收到警方电话。
7. 警方来电显示“警方反诈骗调查组”和号码 `+31 88 662 2880`。
8. 玩家接听后，第一句是“等一下！！！！！不要继续进行确认。”继续后，警方说明他们检测到一个诈骗团伙。
9. 解释结束后不再提供 Continue，原型暂时停在这里。

当前三封 Day 1 邮件：

- Nova Bank Security：可疑邮件，初始未读。
- Civic Workspace：security digest，初始已读。
- Canal Energy：statement，初始已读。

当前内容 ID 仍使用 `case01.*`，这是从早期“多个独立案件”设计遗留的技术命名。文档的新设计使用 `day01.*`。不要为了命名整齐就立即全局重命名；只有在正式引入 Campaign/Day/save schema 且能处理兼容或迁移时再改。

当前警方头像暂时复用了 `system-notification.svg` 铃铛图标，可疑来电使用 `contact-unknown.svg`。这是已知的临时美术选择，不需要为了“完整”立刻生成新资产，除非用户要求。

一个重要设计风险：玩家点击邮件链接后警方立即介入，可能太早救场，减少玩家主动核验和承担后果的空间。文档保留了这个问题。不要擅自重写流程；下一步若要扩展 Day 1，应先和用户讨论是保留教学式拦截，还是让 Browser/银行官方渠道承担验证过程。

### 8. 内容可编辑性要求

用户希望以后可以比较容易地微调每天的事件流程。因此，正式扩展内容系统时应保持数据驱动：

- 日、事件、邮件、电话、条件、效果和后果应尽量由普通 TypeScript 数据对象描述。
- 使用稳定 ID 和 translation key。
- 内容对象中不要塞任意 JavaScript callback；否则非程序员很难编辑，也很难保存、校验和测试。
- UI 组件不应通过 `if (dayId === 'day01')` 等方式绑定具体故事。
- UI 只发出语义动作；控制器读取内容定义、检查条件、更新状态并决定后续事件。
- 一封邮件“已读”与一个事件“已解决”是不同概念。未来事件状态建议至少区分 `unseen / open / resolved / deferred / ignored`，但只有在真正实现控制器时才引入，不要提前造空类型。
- 跨天 flag 数量要少且含义明确，避免组合爆炸。

正式 schema 的规划见 `docs/CONTENT_SCHEMA.md`。保存和运行时状态规划见 `docs/GAME_STATE_AND_SAVE.md`。原则上分三层：

- Desktop state：窗口位置、尺寸、层级、打开/最小化。
- Daily UI state：当天当前选中的邮件、来电/对白状态、临时进度。
- Campaign state：当前天、稳定 flags、已完成事件、可持久化选择和后果。

文档预留的 localStorage key 是：

```text
trust-protocol.settings.v1
trust-protocol.save.v1
```

它们目前只是规划。实现时必须考虑 schema version、损坏数据 fallback 和不覆盖用户已有存档；不要在没有迁移方案时改变 key 或数据含义。

每日内容预算应保持克制：一个主要事件、一个次要事件、1–2 个背景事件、0–1 通电话、2–3 条后果、最多 2 个持久变化。背景信息不能阻止结束当天；未解决的必要事件可在结束前给予一次明确警告。每日后果展示应优先包含“你做了什么”“发生了什么”“这对明天意味着什么”三层，而不是长篇评分报告。

### 9. 多语言规则

游戏必须支持：

- English：`en`
- 简体中文：`zh-CN`
- Nederlands：`nl`

所有用户可见文案都使用翻译 key，通过现有 `src/localization/i18n.ts` 获取。英语资源是类型与 fallback 的基准；新增 key 时必须同步补齐三份 locale 文件，并检查对象结构一致。不要在 Lit template、事件控制器或内容逻辑中直接写显示给玩家的英文/中文/荷兰语句子。

注意不同语言长度差异：荷兰语和英语按钮可能比中文长。不要用固定宽度截断关键操作；允许换行或弹性布局。内容数据应保存 translation key，而不是保存已翻译文本。日期、数字等未来应按 locale 格式化。

详细规则见 `docs/LOCALIZATION.md`。

### 10. 视觉与美术方向

视觉定位是“温暖、编辑式、调查感的虚构操作系统”，而不是炫酷赛博朋克，也不是复制真实银行后台：

- 桌面和应用应熟悉、清楚、易读。
- 证据层级比装饰更重要。
- 不要仅依靠红/绿颜色表达安全与危险；避免提前替玩家判断可疑信息。
- 统一使用现有图标与资产风格，新增资产前先查 `docs/ASSET_REGISTRY.md`。
- 记录资产来源、许可、AI 辅助情况、导出规格和批准状态。
- 早期生成的五张 case 章节图是旧概念资产，不代表必须一张对应新设计中的一天。

权威美术说明见 `docs/ART_DIRECTION.md`，资产清单见 `docs/ASSET_REGISTRY.md`。如果只是简单图标状态，优先复用或编辑现有 SVG/CSS，不要无必要生成大体积位图。

### 11. 无障碍要求

目标为 WCAG 2.2 AA。不得为了赶进度牺牲基本无障碍：

- 所有核心操作最终需要键盘可达、清晰 focus、合理 tab 顺序和可理解的 label。
- Modal 对话框应管理初始焦点、focus trap 和关闭后的焦点恢复。
- 运动效果必须尊重 `prefers-reduced-motion`；当前来电抖动已经这样做。
- 信息不能只靠颜色、声音或动画表达。
- 缩放、窄屏和三种语言下都要保持关键文案可读。

当前已知缺口是窗口拖动和右下角缩放只有 pointer 操作，尚无键盘替代。用户此前明确说缩放第一版先不考虑键盘替代，所以不要把这个缺口当成本轮必须擅自扩展的任务；但正式发布前需要重新评估。详见 `docs/ACCESSIBILITY.md`。

### 14. 推荐的接手流程

接手后不要直接开始增加功能。先执行：

1. 读取 `README.md`、`AGENTS.md` 和本提示词提到的相关文档。
2. 运行 `git status --short`，识别当前未提交范围。
3. 运行 `npm test` 与 `npm run build`，建立基线；若失败，先报告现状并区分既有问题和你的问题。
4. 搜索当前用户要求涉及的组件、事件、翻译 key 和测试。
5. 用 2–4 步写出最小实现计划，每一步都带验证方式。
6. 修改最少的代码和文档。
7. 运行相关测试、完整构建，并按需要手动验证浏览器流程。
8. 最后用中文简洁说明：完成了什么、验证结果、改了哪些关键文件、仍有什么已知限制。

如果用户只是询问或讨论设计，不要因此修改代码。如果用户说“先不改动代码”，只能分析和讨论。如果用户提出一个较大的功能，先切成第一个可玩的垂直切片，但不要在没有必要选择时反复要求确认。
